How ESAM Finds Answers

Four real questions about the SYNTH-LTV vehicle, answered five ways: with no retrieval, with document search, with a graph database (two query languages), and with ESAM's hybrid. Every answer quoted is a real GPT-5.1 run on the same documents. The kind of question decides which method works.

2The vehicle as a graph

A graph stores things and the relationships between them. This is a simplified piece of the SYNTH-LTV baseline: three systems, four subsystems, their documents, and the EBC1 brake-status message that crosses between them.

Vertices

The things: the vehicle, systems, subsystems, documents. Each box below is a vertex.

Edges

The relationships: is part of, has document, sends EBC1 to. Each line is an edge, and it has a direction.

Properties

The facts stored on them: WBS code, safety-critical (red dot), whether a link is confirmed or still a candidate (dashed).

In ESAM the graph is built from the SE-owned baseline, not guessed by AI. That's why it can be trusted to say what is connected, and what is missing (red dashed boxes).

    4What each approach costs
    
      
    Measured on the ESAM learning stack (a 4-core laptop; PostgreSQL with pgvector; the embedding model on CPU). Speed is not
        the deciding cost. The deciding costs are what must be built and kept current, and how much text goes to the model.
    
      
    
        
    Time to find the evidence
    Per question, before the model starts writing. The model's own answer takes several seconds more in every case.
    
        
    Text sent to the model
    Per question, in tokens (about ¾ of a word each). More text costs more and can dilute the answer. A graph walk sends nothing to a model unless one is asked to write up the result.
    
      
    
      
    
    
    
  
    

  
    
    
    
      
    5Is hybrid actually better? What others found
    
      
    Published results from industry and research, including where graphs and hybrids did not help.
    
      
    
      
    
        
    Our reading of the evidence
    
        
      
          
    • Document search wins on simple lookups. It's as accurate as a graph and cheaper. A hybrid adds cost there for little gain.
      • 
          
    • Graphs win on connection and absence questions. "Who is affected", "what is missing", "what verifies this": document search cannot answer these reliably.
      • 
          
    • Combining both gives the best answers, at a price. More text goes to the model, and studies saw lower precision when everything is sent. Routing each question to the right source keeps the cost down.
      • 
          
    • The quality of the graph decides everything. Graphs built automatically by AI miss about a third of the facts in one study. ESAM avoids this because the graph comes from the SE baseline.
      • 
          
    • SE work is mostly connection and absence questions. That is why ESAM is hybrid. A hybrid would be over-engineering for a pure document library.
      • 
        
    
      
    
    
    
  
    

  
    
    
    
      
    6What this means for the pilot
    
      
      
        
    • The baseline is the asset. The graph is only as good as the YAML baseline the SE team maintains. Budget SE time for it the way you would for any configuration-controlled artefact.
      • 
        
    • The pilot's graph runs in PostgreSQL with the same walks shown in the Gremlin and Cypher tabs. JanusGraph (Gremlin) is the full-deployment target. Neo4j (Cypher) is not approved and is shown only because most published work uses it.
      • 
        
    • Treat "the document doesn't exist yet" as a finding. Only the hybrid can say it with certainty, because only the graph knows what should exist.
      • 
        
    • Next steps: route each question to the right source automatically (the planned Query tab in the SE Cockpit), and define the programme vocabulary (ontology) so routing and gap checks get sharper.
